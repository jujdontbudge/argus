1. A correction to the baseline check the ticket itself prescribes
------------------------------------------------------------------------------
The ticket's own cleanup check is:

  pgrep -f 'bin/bun.*cli\.ts watch' | wc -l   -> 0

Run inside a shell whose own command line contains that pattern, `pgrep -f`
MATCHES ITS OWN INVOKING SHELL. The first time this run issued the check it
returned 1 with no watcher running at all. Proof:

  $ pgrep -f 'bin/bun.*cli\.ts watch' | wc -l
         1
  $ ps -Ao pid,command | grep -E 'bin/bun.*cli\.ts watch' | grep -v grep | wc -l
         0

Every watcher count in this file is therefore taken with `ps`, and the `pgrep`
form is reported beside it in §9 for the ticket's sake. A future ticket that
trusts the bare `pgrep` number will chase a watcher that does not exist.

  #2  Add a wordCount helper to src/text.ts
  #3  Add a median helper to src/numbers.ts

THE TRACKER IS A SHIM, AND THAT IS A LIMIT OF THIS RUN. The sandbox repo has
no GitHub remote and must never get one, but Argus reaches its tracker only
through `gh`. So `$SANDBOX/bin/gh` is a local issue store implementing exactly
the `gh` surface Argus uses (issue list/view/edit/close/comment/create, api
user, api .../dependencies/blocked_by, api .../sub_issues, repo view, label
list/create). It logs every call and FAILS LOUDLY on any verb it does not
implement, so a gap shows up as an error rather than as a plausible empty
result. What this run therefore does NOT prove is Argus against real GitHub
semantics — sub-issue graphs, dependency edges and assignment races are all
stubbed to the empty/simple case.
