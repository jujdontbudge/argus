******************************************************************************
FINDING 1 (BLOCKER, argus bug, NOT a skill bug and NOT a harness artifact)
  Every Codex worker Argus deploys is READ-ONLY unless the machine's personal
  codex config happens to grant write access.
******************************************************************************

  Argus's Codex route (src/deploy/routes.ts:112-124) spawns exactly:

    codex exec --json -c model_reasoning_effort=high <dispatchPrompt>

  It sets the reasoning effort and NOTHING about the sandbox or approval
  policy. `codex exec` defaults to a read-only sandbox, so a worker cannot
  write the file it was dispatched to write.

  On Johan's machine this is invisible, because his own live config says:

    $ grep -nE '^\s*(approval_policy|sandbox_mode)' ~/.codex/config.toml
      10:approval_policy = "never"
      11:sandbox_mode = "danger-full-access"

  So production inherits write access from a PERSONAL preference file that
  Argus does not own, does not set and does not check.

  This is not the scratch home's fault. `argus up` DOES write to
  $CODEX_HOME/config.toml — it wrote exactly this, and only this:

    # argus:notify:begin
    notify = ["/Users/.../bun","/Users/.../scripts/codex-notify.ts"]
    # argus:notify:end

  Argus reaches into the codex config to install its notify hook and, while it
  is there, does not set the one policy without which its workers cannot work.
  Any machine, CI runner, or fresh checkout whose codex config lacks
  `sandbox_mode` gets six silent `blocked-on-human` events and zero lines of
  code, which is what this run got.

  #88 made Codex "the default implementer". On the evidence of this run, a
  deployed Codex worker has never successfully written a file on any machine
  but Johan's.

  Not fixed here: the fix is a one-line change to a production route
  (`--sandbox workspace-write`, or `-c sandbox_mode=workspace-write`), and the
  choice between granting workspace-write and granting full access is a policy
  call about what an unattended worker may touch. That belongs to Johan and to
  its own ticket, not to an acceptance run. FILED, not fixed.

6. Did the new tab path behave? YES — open and close, both live
------------------------------------------------------------------------------
#95's `src/deploy/tab.ts` ran live for the first time here, and it did exactly
what it says.

  workspaces before the drive   8
  workspaces at every check     8
  workspaces after the drive    8      <- NEVER moved
  surfaces before the drive    25

Per deployed worker Argus issued, in this order:

  cmux --id-format both tree --all --json          (resolve + membership check)
  cmux new-surface --type terminal --workspace 2D3B8B38-...-8F1157CE2E10
  cmux --id-format both tree --all --json          (re-resolve the new surface)
  cmux rename-tab --workspace 2D3B8B38-... --surface E4E51E17-... argus #1

and on reap:

  cmux close-surface --surface E4E51E17-... --workspace 2D3B8B38-...

The tab is opened in the workspace Argus was already running in — the
`CMUX_WORKSPACE_ID` this run passed in deliberately, because without it
tab.ts degrades to "no tab" and the path would not have been exercised at all.
Every handle is re-resolved against `tree --all --json` before any mutating
verb, which is the guard tab.ts's docblock promises.

The surface UUID is recorded in the registry row beside the session id, so a
tab is traceable back to its ticket:

  {"agent":"codex","sessionId":"01a04011-df0d-7482-a912-ad02592f50d4",
   "ticket":"1","worktree":".../repo-worktrees/ticket-1",
   "workspace":"2D3B8B38-C9FC-46F4-A512-8F1157CE2E10",
   "surface":"E4E51E17-5D62-4496-B0F8-B4A43C40FE70", ...}

Tabs are closed by the NEXT dispatch's recovery pass, not by the dying worker
itself — a crashed worker's tab therefore lingers until something else runs.
That is a design consequence worth knowing, not a defect: it is what makes the
crash path recoverable at all. In this run every tab opened was eventually
closed, and the workspace count never moved off 8.

******************************************************************************
FINDING 4 (argus bug) — `argus dispatch --help` is not help. It DISPATCHES.
******************************************************************************

  Hermes's second-ever argus call was `argus dispatch --help`, the obvious way
  to learn a subcommand. `src/cli.ts:405` is:

    if (args[0] === "dispatch") return dispatch();

  `dispatch()` takes no parameters and never inspects `args`. So `--help` is
  silently discarded and a REAL dispatch pass runs — claiming tickets, cutting
  worktrees, spawning paid agent sessions. Hermes was saved only by being in
  the wrong directory at that moment:

    $ argus dispatch --help          (from outside the repo)
      argus dispatch: current directory is not inside a git repository

  Inside the repo the same keystrokes deploy the frontier. `--help` is
  documented at top level only (`const HELP`, src/cli.ts:7-34); no subcommand
  accepts it. The same trap applies to `argus complete --help` and
  `argus signals --help`.
