2. THE RESOLVE-THEN-ACT RACE, measured — and it is not what we believed
------------------------------------------------------------------------------
The ticket asks: resolve a ref, mutate the workspace, then use the ref. Does
the ref name something else by then? Measured on four throwaway tabs of my own
in workspace:1, every step bracketed by a whole-machine tree snapshot.

  R1  create three tabs             -> surface:63, surface:64, surface:65
                                       (new-surface PRINTS the ref, see §6)
  R2  close surface:64 BY UUID      -> exit 0. surface:63 and surface:65 kept
                                       their refs exactly. NO renumbering.
  R3  create a fourth tab after
      surface:64's ref was freed    -> got surface:66, NOT surface:64.
                                       A freed ref is NOT recycled.
  R4  reorder-surface surface:65
      to index 0                    -> exit 0. surface:65 kept its ref; only
                                       its position moved. NO renumbering.

CONCLUSION, and it corrects our own documentation. Short refs do NOT remap.
They come from a monotonic counter (this cmux process is at 66 while the oldest
live surfaces still hold refs 1-23), they survive close, create and reorder,
and a freed ref is never handed to a different surface. The skill
(`skills/argus-orchestrator/SKILL.md`) said "short refs are positional and cmux
REMAPS them as surfaces open and close". That is wrong, and it is a dangerous
kind of wrong, because it implies re-resolving immediately before the call is
the fix. It is not, and the real mechanism is worse:

  A ref that resolves to NOTHING is not an error. It is a redirect.

So the ref that killed a tab was never a ref that pointed somewhere else. It
was a ref that pointed NOWHERE — freed by an earlier close, or minted by a
previous cmux process — and cmux answered for the focused surface instead.

THE RACE THAT REMAINS IS REAL, AND UUIDs DO NOT CLOSE IT. Resolve-then-act is
not atomic: between `tree --all` and `close-surface`, another session can close
the surface you just resolved. What UUIDs change is the CONSEQUENCE of losing
that race. Lose it holding a UUID and the verb errors `not_found` and closes
nothing. Lose it holding a ref and the verb closes whatever Johan is looking at
and exits 0. The window cannot be removed from outside cmux; the blast radius
can, and only the handle form removes it.

TWO MORE THINGS THAT DEFEAT "I CHECKED FIRST":
  - Focus moves on its own. Across this run `identify.focused` walked
    surface:2 -> surface:6 -> surface:4 with no action by me, because other
    sessions were working. A safety argument that ends "and I verified what was
    focused" has already expired by the time the next call runs.
  - Refs are renumbered from scratch when cmux restarts. A ref persisted into a
    registry row outlives the process that gave it meaning; a UUID persisted
    the same way just stops resolving. Not measured — measuring it means
    restarting Johan's cmux, which I refused (§8).

  A THIRD ADDRESSING FORM, undocumented in our tree: cmux accepts a bare index
  in the same flag, and it is positional and DIFFERENT from the typed ref.
  `cmux list-pane-surfaces --workspace 1` answered for a different workspace
  than `--workspace workspace:1`. Dropping the prefix silently changes which
  workspace you mean.

3. RECOMMENDATION: destructive cmux verbs take UUIDs ONLY
------------------------------------------------------------------------------
The ticket asked me to measure before agreeing that UUID-only is strictly
stronger than resolve-then-act. Measured, and I agree, but for a sharper reason
than the one offered:

UUID-only is not a stronger version of the same defence. It is a DIFFERENT KIND
of defence. Resolve-then-act is a check the caller performs and can lose; the
handle form decides how the BINARY behaves when the check has already been lost.
Guard and UUID are not alternatives — the guard narrows the window, the UUID
makes losing the window a no-op — but if only one can be relied on it must be
the UUID, because it is the only one that still holds when our code is wrong.

Concretely: `close-surface` given a dead UUID exits 1 and closes nothing
(measured twice above, tree diff empty both times). Given a dead ref it exits 0
and closes the focused surface. No amount of pre-resolution changes either.

Status in the tree today: production already complies. `openWorkerTab` returns
`surface.id` (a UUID) and `closeWorkerTab` is called with it; `CMUX_WORKSPACE_ID`
is a UUID. The gap was in what we TELL agents, and in one selector — see §4/§5.

4. A PRODUCTION BUG THIS DRIVE FOUND: mission delivery rejected UUIDs
------------------------------------------------------------------------------
`missionSession` in `src/events/notify.ts` selected the mission row with

    session.agent === "hermes" && session.workspace?.startsWith("workspace:")

That prefix test predates #95. Since #95 a worker's tab is addressed by the
UUID in `CMUX_WORKSPACE_ID`, so the selector rejected every UUID-addressed
mission and `notifyMissionControl` degraded with "Hermes mission-control
workspace is absent from the registry" — for a workspace that was present and
resolvable. It also selected FOR the short-ref form, i.e. for the one handle
form measured above to fail OPEN.

Counterfactual, measured rather than argued. Same scratch registry, workspace
written as a UUID, cmux stubbed so only the selector varies:

    with the #90 fix   -> {"status":"sent"}
    predicate reverted -> {"status":"degraded","reason":"Hermes mission-control
                           workspace is absent from the registry"}
    fix restored       -> {"status":"sent"}

Fixed here (the selector now accepts either form; resolution stays where it
belongs, in `createCmuxSend`, which checks the handle against cmux's own
inventory and refuses). Regression test:
`src/events/events.test.ts` — "#90: a mission workspace addressed by UUID is
found, not reported absent".

This is why the ticket exists. The fake runner in `src/events/scenarios.ts`
answers `workspace:scenario-7`, a short ref, so every test of this path used the
one form the code accepted. A real cmux hands out UUIDs and the bug appeared on
the first live call.

6. SMALLER THINGS THE REAL BINARY CONTRADICTED
------------------------------------------------------------------------------
`src/deploy/tab.ts`'s docblock says "cmux 0.62.2 prints no ref for
new-surface". It does:

    $ cmux new-surface --type terminal --workspace <uuid>
    OK surface:63 pane:1 workspace:1

The code does not actually depend on this — it never parses stdout, it diffs
the inventory before and after — and the diff is the better method anyway,
because what `new-surface` prints is a SHORT REF while the diff yields the UUID.
So the reasoning is wrong and the behaviour is right. Left as-is and recorded
here rather than "fixed" into something that reads the ref off stdout.

The three mission-control verbs SPEC.md:156-158 promises all EXIST on the real
binary — `cmux set-status`, `cmux set-progress`, `cmux markdown open` each
