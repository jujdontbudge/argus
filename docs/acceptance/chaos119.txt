2. H1 + H2 — THE FIX, AND WHY IT IS THE SMALLEST ONE THAT WORKS
--------------------------------------------------------------------------------

  H1. `healthPidSeen` returned a bare `false` when no sample in the window
  carried the replacement pid, and `leaseTakeover` reads `false` as failure. It
  had no state for "the sampler never got to look", although the same file nulls
  `inBudget` and `leaseTakenOver` when `newPid` is null and filters those nulls
  out of the verdict.

  The fix introduces a second, narrower OBSERVABILITY window: from the restart
  to the earlier of `restart + LEASE_TAKEOVER_MS` and the moment that
  replacement pid was ITSELF killed. The two windows are used asymmetrically,
  and the asymmetry is the whole point:

      seen anywhere in [restart, restart + LEASE_TAKEOVER_MS]       -> true
      not seen, and >= 1 usable sample in the observability window  -> false
      not seen, and 0 usable samples in the observability window    -> null

  Why not narrow both. `health.json` is a FILE, not a process. Once a
  replacement writes its pid there, that pid stays on disk until the next
  replacement overwrites it, so a sighting proves a write that already happened
  and is sound wherever in the 120 s bar it lands — including after that pid is
  dead. This is not hypothetical. The obvious first cut, narrowing both tests
  symmetrically, was written and run first, and on this data it turned idx 42
  (pid 69061) from a correct `true` into a `null`:

    $ # symmetric version, since discarded
    {"idx":42,"eye":"retro","phase":"brake","killedPid":67678,"newPid":69061,
     "sealed":true,"v2":null,"leaseObservations":0,
     "windowEnds":"2026-08-28T18:04:04.489Z"}

  That replacement wrote health, was killed, and was then observed from the file
  it had already written. The symmetric fix would have traded two false
  negatives for one lost true positive. The asymmetric one loses none, and the
  final output still shows the trace of it — of the 41 judged kills, 40 were
  judged on 1 usable in-lifetime sample and one (idx 42) on 0, resolved `true`
  by a post-death sighting:

    v2 leaseJudged: 41 of 43
    obs distribution for judged: {"0":1,"1":40}

  H2. `bystander` counted supervisor restart lines across the whole log with no
  teardown exclusion, while `noMessageLoss` in the same file excludes the last
  TAIL_GRACE_MS = 120_000 ms by design and says why. The fix applies that same
  exclusion, reusing that same `graceFrom` boundary. No new threshold.

  Dating a line took one step, because supervisor.log carries NO timestamps:

    $ tail -1 /private/tmp/argus-chaos-mxErsY/supervisor.log
    argus supervisor: archiver watcher pid 92523 for
      /private/tmp/argus-chaos-mxErsY/repo-1 exited with code 0; restart 1/5 in 1000ms

  A line names the pid that exited, and that pid cannot have exited BEFORE the
  last sample that still listed it as a live watcher. That last sighting is a
  sound LOWER BOUND on the exit, and a lower bound is all this needs: if the
  bound is already inside the grace window, the exit is too. The comparison can
  therefore only ever exclude a line when the exclusion is certain. A line whose
  pid never appeared in any sample cannot be dated and is JUDGED, not excluded,
  so the fix cannot quietly widen itself into an amnesty.

  On this run:

    bystander lines seen / judged / excluded:  1 / 0 / 1

        "line": "argus supervisor: archiver watcher pid 92523 for /private/tmp/argus-chaos-mxErsY/repo-1 exited with code 0; restart 1/5 in 1000ms",

4. H3 — CORRUPTION, RE-RUN AGAINST A POPULATED CHECKPOINTED ARCHIVE
--------------------------------------------------------------------------------

  WHY A NEW FILE AND NOT AN IN-PLACE EDIT. #119 allows an in-place fix where it
  is purely mechanical. This one is not. Deciding HOW to make the damage land on
  live data — force a checkpoint, or seed until the file is large enough, and
  how large is large enough — is experimental design, not a typo. And
  chaos117.txt §6 H3 and §7 quote corrupt117.ts's arithmetic to explain why two
  of three modes established nothing; editing that file would leave the filed
  finding unreproducible from the tree. So corrupt117.ts stays as committed in
  07a392e and scripts/chaos/corrupt119.ts carries the fix.

  WHAT CHANGED. Four things, and OBSERVE_MS, POLL_MS, the LOUD and RECOVERABLE
  definitions, the single unsupervised watcher and the reporting shape are all
  unchanged, so the numbers stay comparable with #117's.

    1. A SEED phase replaces the fixed 25 s settle. It appends traffic in
       batches and runs `PRAGMA wal_checkpoint(TRUNCATE)` each tick until the
       MAIN file holds at least MIN_DB_PAGES = 16 pages. The checkpoint is what
       moves rows out of the WAL and into the b-tree pages this scenario is
       supposed to be damaging. A checkpoint writes no row and biases nothing.
    2. `corrupt()` now REFUSES page-garbage, recording why, if the computed
       offset is not a whole page strictly inside the file. The write-past-EOF
       that voided #117's result can no longer happen while still reporting
       `applied: true`.
    3. A CONTROL: immediately after the damage a fresh read-only connection runs
       `PRAGMA integrity_check` and the answer is recorded. #117 could not tell
       "Argus did not notice" from "nothing was broken". That distinction is now
       a recorded fact instead of an inference.
    4. Modes are selectable on argv, so page-garbage can be re-run alone.

  A FIFTH CHANGE, FOUND BY RUNNING IT. The one-line console summary printed
  `loud=${firstErrorAfterMs !== null}`, and `firstErrorAfterMs` only ever
  watches health.json and watcher liveness — it never looks at stderr, which the
  LOUD definition explicitly counts. Run A therefore printed `loud=false` while
  its own recorded `loud` object showed 90 stderr lines. The recorded JSON was
  always right; only the summary contradicted the file's own definition, and a
  summary is what gets read instead of the JSON. The definition is unchanged;
  the line now reports all three channels separately, and the run was repeated
  so the quoted output matches the file at HEAD. Run A and run B agree on every
  other number.

5. H4 — DISK FULL, RE-RUN TWICE
--------------------------------------------------------------------------------

  WHY THIS ONE WAS FIXED IN PLACE. #119's own text calls the argv index a
  one-line mechanical fix with no judgment attached, and it is: under
  `bun -e '<code>' <arg>` there is no script path in argv, so the argument lands
  one slot earlier than under `bun <script.ts> <arg>`. Confirmed again this
  session:

    $ bun -e 'console.log(JSON.stringify(process.argv))' /tmp/somepath.db
    ["/Users/johansardar/.bun/bin/bun","/tmp/somepath.db"]

  Reading `argv[2]` yielded undefined, `new Database(undefined, {readonly:true})`
  opened an anonymous database, and that combination throws — which is why every
  row count in #117's run recorded the string "ERR Cannot open an anonymous
  database in read-only mode.". No verdict depended on it, chaos117.txt §6 H4
  records the defect with its own standalone reproduction, and the finding
  therefore stays reproducible without the broken file. Fixed in place, both
  call sites: `rows()` and the integrity check.

  THE SECOND CHANGE, the "consider" in #119. #117's reading was that the
  archiver was probably never actually denied a write, because `dd bs=1m` stops
  at the first 1 MiB write that fails and can leave most of a megabyte free,
  which `df -m` rounds to 0. The fill is now graduated — bs=1m, then bs=4096,
  then bs=512 — and the real free space is recorded at kilobyte resolution
  instead of megabyte. That change is gated behind
  ARGUS_CHAOS_DISKFULL_TIGHT (default 1) so the argv fix could be validated
  against #117's EXACT conditions first. Two variables are never moved in one
  run. The message cadence is untouched, so row counts stay comparable.

  The blast-radius design is unchanged: one fixed-size 20 MiB image under
  /private/tmp, attached -nobrowse at a private mountpoint, detached by the
  captured device node from an EXIT/INT/TERM trap.

6. PRODUCTION FINDINGS — REPORTED, NOT FIXED
--------------------------------------------------------------------------------

  #119 is a harness ticket. Both of these are in `src/`, both were found by the
  re-runs, and neither is fixed here. Filed for the dispatcher, in the same
  discipline #117 used for H1-H4.

  P1  A corrupted archive page stops archiving SILENTLY as far as any operator
      surface is concerned. §4: 90 seconds, 0 rows archived, every attempt
      raising "database disk image is malformed" on stderr, while health.json
      holds `lastError: null`, `backlog: 0`, and a `lastSuccess` that keeps
      advancing to the current second. The advancing `lastSuccess` is the sharp
      part: it is not merely failing to report the error, it is actively
      reporting success. `argus status` cannot distinguish this archiver from a
      healthy one. This is the same SHAPE as the bug 41cbcf5 fixed under #117
      ("a resumed watcher archived nothing, silently, forever"), reached by a
      different route, which suggests the reporting path rather than either
      call site is the thing worth looking at.

  P2  ENOSPC on the health file crashes the watcher, and the crash is
      permanent. §5: uncaught at src/supervisor/health.ts:84, exit code 1,
      within 5 s of the volume filling. Two things make it worse than a crash.
      First, the file that killed the archiver is the one whose only job is to
      SAY the archiver is unwell — the reporting channel is the failure. Second,
      `#persist` does `this.#write = this.#write.then(...)`: once that stored
      promise rejects, every later write chains onto a rejected promise, so
      recovery is impossible even after space returns, which is what the flat
      90 s recovery window shows. Under a supervisor the process would at least
      be restarted; unsupervised, as here, it stays dead.

  Neither is in #119's scope and neither was touched.
