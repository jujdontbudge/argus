Hermes constructed a ref-shaped handle and persisted it. Here is the row, from

Two separate problems in one row.

  (a) `surface:B56BDD1F-3094-41D7-A405-D3DBDAF4DB9C` is a MALFORMED HYBRID.
      Hermes took the surface UUID Argus recorded and prefixed it with
      `surface:`. That is neither a short ref nor a UUID.

      MEASURED against the real 0.62.2 binary, with a bogus UUID so nothing real
      was touched:

        cmux read-screen --surface surface:00000000-0000-0000-0000-000000000000
          -> exit 1  "Error: Invalid surface handle: surface:0000... (expected
                      UUID, ref like surface:1, or index)"
        cmux list-pane-surfaces --workspace workspace:<a real workspace UUID>
          -> exit 1  "Error: Invalid workspace handle: ... (expected UUID, ref
                      like workspace:1, or index)"

      The hybrid FAILS CLOSED. It is rejected at parse time, before resolution,
      so it can never be redirected onto a focused surface. It is a bug in the
      record, not a hazard. If it had ever been passed to `close-surface` it
      would have closed nothing.

  (b) `"workspace":"workspace:1"` IS the fail-open shape, and it is now durable.

      This is the one worth Johan's attention. `workspace:1` is a plain numeric
      short ref, and #90's measurement of what those do was re-confirmed live
      during this run, independently:

        cmux list-pane-surfaces --workspace workspace:9999   -> exit 0, answered
        cmux read-screen        --surface   surface:9999     -> exit 0, and it
            RETURNED THE CONTENTS OF ANOTHER SURFACE'S SCREEN
        cmux list-pane-surfaces --workspace 00000000-...     -> exit 1, not_found
        cmux read-screen        --surface   00000000-...     -> exit 1

      A ref that resolves to nothing exits 0 and acts on the focused surface.
      A UUID that resolves to nothing exits 1 and acts on nothing.

      The corrected skill states this correctly and even states this exact
      consequence: "a ref persisted in a registry row outlives the process that
      gave it meaning." Hermes then persisted one, into sends.jsonl, which is
      the durable provenance file the same skill tells it to write. The skill
      names the hazard and does not forbid the act that creates it.

WHAT SAVED THIS RUN, and it was not the skill. Hermes never passed either handle
to cmux. It issued ZERO `cmux send` calls, because it resumed ticket #3 through
`codex exec resume` instead (D3). The registry row's workspace and surface
fields were decorative — written to satisfy the provenance rule, never used to

`workspace:1` is what it would have sent to.

  RECOMMENDATION (not made here — it is a skill change, and this run's job was

  `argus up` rewrites it wholesale. The next converge would drop the trust
  entry without saying so.

  This is a consequence of TOML section semantics rather than of anyone's
  mistake: a `[table]` header captures every key after it until the next header,
  so appending a table before the end-marker swallows the marker's own scope.
  It is worth a guard — either Argus refusing to rewrite a block whose contents
  it did not write, or placing its markers so a trailing table cannot be
  captured. FILED, not fixed.
