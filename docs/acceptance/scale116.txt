5. THE ONE FAILING COMPONENT — provenance cursor = NO LONGER FLAT
--------------------------------------------------------------------------------

  The overall FAIL is driven entirely by this, on repos 0 and 1:

    repo 0   provenance cursor  NO LONGER FLAT   soak traffic  WITHIN BUDGET
                                                 sqlite backlog WITHIN BUDGET
    repo 1   provenance cursor  NO LONGER FLAT   soak traffic  WITHIN BUDGET
                                                 sqlite backlog WITHIN BUDGET
    repo 2   all three          INSUFFICIENT DATA

  No query in any repo breached the absolute backstop: `backstopBreached` is
  false in all nine judgements. Peak observed search latencies were 38.436 ms
  (repo 0) and 227.780 ms (repo 1) against a 5,000 ms backstop.

  WHAT THE RULE IS. `provenance cursor` is #110's flat-class query. It has
  `barMsPer1kRows: null` — #105 measured its slope at 0.4041 ms/1k rows with a
  95% CI of [-1.303, +2.111], too wide to turn into a number, so latency.ts
  judges it by SHAPE instead of by size. If the CI includes zero it is STILL
  FLAT. If the CI excludes zero, growth is real and the only question is what
  explains it: `|r(rows)| >= |r(load)|` returns NO LONGER FLAT, otherwise
  GREW WITH LOAD, NOT CORPUS. Ties go to NO LONGER FLAT deliberately, so that
  the asymmetry can never be used as an excuse.

  WHAT THIS RUN MEASURED.

    repo   OLS      Theil-Sen   95% CI              r(rows)   r(load)
    0      1.7117    1.5514     [1.3309, 2.0924]     0.810    -0.169
    1      1.9079    1.9022     [1.8586, 1.9572]     0.931    -0.136

  Both CIs exclude zero, and in both repos the rows correlation dominates the
  load correlation by roughly five to seven times, with the load correlation
  actually NEGATIVE. The rule fires cleanly and unambiguously. There is no
  argument that the verdict was misapplied.

  WHAT IT DOES NOT MEAN, WITH THE NUMBERS. Compare the same query across the
  three runs that have now measured it:

    run    context                         OLS      Theil-Sen  CI              verdict
    #105   1 repo, 5 eyes, 21,066 rows    0.4041      —        [-1.303, 2.111] flat (bar declined)
    #109   1 repo, phased, 190,452 rows   1.4574   2.0492      [0.760, 2.155]  GREW WITH LOAD
    #116   repo 0, 3 repos, 12,957 rows   1.7117   1.5514      [1.331, 2.092]  NO LONGER FLAT
    #116   repo 1, 3 repos, 93,408 rows   1.9079   1.9022      [1.859, 1.957]  NO LONGER FLAT

  Every #116 point estimate and every #116 confidence bound lies INSIDE the
  interval #105 measured for this query and declared too wide to bar. 2.0924
  and 1.9572, the two upper bounds here, are both below #105's own upper bound
  of 2.1113. #109's Theil-Sen of 2.0492 was higher than either #116 repo's. On
  the magnitude of the slope, this run is unremarkable and entirely consistent
  with its two predecessors.

  What changed is the ATTRIBUTION, and the reason is in the run's design.
  #109 had four traffic phases including a dead stop, so its load moved a lot
  and its rows correlation was 0.136 against a load correlation of 0.272 —
  load won, and the verdict was GREW WITH LOAD. This run held each repo's rate
  constant for 150 minutes, so rows climbed almost monotonically while the
  one-minute load average stayed in a narrow band (1.97 to 8.36 over the
  settled window). Under a near-constant rate, `rows` and `elapsed` are close
  to collinear — the exact confound #109's whole design existed to break — and
  load has almost nothing left to explain. A constant-rate run is therefore the
  condition under which the flat-class rule is MOST likely to return NO LONGER
  FLAT, independent of whether the system got worse.

  Stated as plainly as the pre-registration requires: the pre-registered
  verdict is FAIL and it is not being argued away. The honest reading is that
  this is a shape verdict on an unbarred query whose measured size sits below
  the house numbers, produced under traffic conditions chosen to make the shape
  test strict. What it establishes is that `provenance cursor` grows with
  corpus size on this data at a rate near 1.7-1.9 ms per 1,000 rows. It does
  not establish that anything regressed relative to #105, #109 or #110 — the
  two BARRED queries, which are the ones with a calibrated bar to regress
  against, both returned WITHIN BUDGET on both driven repos.

  THE BARRED QUERIES, since they are the ones with a real bar:

    query             bar    repo0 OLS  repo0 T-S   repo1 OLS  repo1 T-S
    soak traffic      5.2      2.4352    2.3981      2.2255    2.2344
    sqlite backlog    4.7      2.1205    2.0976      2.0627    2.0559

  Against #110's calibration (soak traffic 2.1542, sqlite backlog 1.5182) and
  #109's out-of-sample confirmation (2.3414 and 2.0815), #116's driven repos
  land in the same place — soak traffic 2.23-2.44 against a bar of 5.2, sqlite
  backlog 2.06-2.12 against a bar of 4.7. ADR-0003's budget survives being run
  three repos at a time under a shared HOME. That is the fourth independent
  confirmation of the rate-invariant constant, and the first multi-repo one.

  REPO 2's INSUFFICIENT DATA is correct, not a gap. Its row count was constant
  at 4,016 for the whole settled window, so `correlationWithRows` is null —
  there is no variance in the regressor to fit against. latency.ts returns
  INSUFFICIENT DATA rather than a number, and the sealed docblock carries that
  through by name as neither a pass nor a fail. The enormous CI bounds printed
  beside it (±5.65e13 and similar) are the arithmetic signature of that
  degenerate fit, not a measurement. Repo 2's absolute latencies were tiny:
  max 5.527 / 0.235 / 2.318 ms across the three queries.

5b. A FINDING IN THE SEALED FILE: ITS DOCBLOCK AND ITS CODE DISAGREE.
    REPORTED, NOT PATCHED. THE FILE WAS NOT EDITED.

    `analyze116.ts`'s closing docblock paragraph states the overall rule as:

      "OVERALL: PASS only if isolation, frozen, attribution, scale and the RAM
       guard all pass AND no repo's latency verdict is a REGRESSION or a
       backstop breach."

    The code that implements it (analyze116.ts, the `failed` expression in
    `judgeRun`) tests three strings, not two:

      entry.report.verdict.includes("REGRESSION") ||
      entry.report.verdict.includes("BREACHED") ||
      entry.report.verdict.includes("NO LONGER FLAT")

    NO LONGER FLAT is in the code's fail set and is absent from the prose. On
    this run that discrepancy is decisive and nothing else: under the code's
    rule the run is FAIL, under the prose rule it would be PASS, and no other
    component differs.

    This report takes the CODE's rule. Three reasons. The code is what was
    sealed and what actually executed; the prose paragraph is a summary of a
    document whose §6 already says growth is "reported per repo, judged only by
    #110's imported bars", so the prose is loose in more than one place; and
    choosing the more permissive of two pre-registered readings after seeing
    that it flips a FAIL to a PASS is precisely the move pre-registration
    exists to forbid. The stricter rule ran, so the stricter rule stands.

    This is filed as a defect in the harness for a follow-up ticket to fix
    BEFORE its next run, in the same way #109's harness scripts stayed sealed
    and their problems were reported rather than patched mid-flight. It is not
    a production-code bug: `scripts/scale/analyze116.ts` is analysis-only and
    ships nothing. No production code was changed by this analysis pass.

8. WHAT THIS RUN DID NOT ESTABLISH
--------------------------------------------------------------------------------

  1. IT DID NOT ESTABLISH THE SCALING EXPONENT IN N. N was 3 and only 3. Every
     scaling statement here — RSS 0.937x linear, CPU flat in own-repo ingest —
     is one point plus #105's N=1 anchor. #116's own ask allowed scaling up
     "if time and RAM guard allow"; the RAM guard allowed it (49.1% used) but
     the run did not do it. N=5 and N=10 remain unmeasured. The honest state of
     the linearity claim is: it passes at N=3 with room to spare, and nothing
     is known about where it stops passing.

  2. IT DID NOT ESTABLISH THAT ISOLATION HOLDS UNDER SEPARATE HOMES, OR UNDER
     CONCURRENT WRITES TO THE SAME SESSION FILE. All three repos shared ONE
     HOME, which is the hard case for `sessionsForRepo` and the right one to
     test. But #116's ask 1 said "separate scratch HOMEs"; this run
     deliberately used one, which makes the leak test strictly harder but means
     the multi-HOME path is untested here.

  3. IT DID NOT ESTABLISH ANYTHING ABOUT CPU AGAINST A BAR. §6 reports 25.263
     CPU-seconds per 1,000 rows and stops. There is no prior measurement to
     compare it to and none is manufactured. A follow-up must pre-register a
     CPU bar BEFORE its run or it will be in the same position.

  4. IT DID NOT RESOLVE WHETHER `provenance cursor` GROWING WITH CORPUS IS A
     PROBLEM. §5 shows the slope is inside #105's own confidence interval and
     that the verdict flipped on attribution, not magnitude. Deciding whether
     ~1.7-1.9 ms/1k rows on the flat-class query is acceptable requires a bar
     for that query, which #110 explicitly declined to set because its CI was
     too wide. This run's repo-1 CI is narrow — [1.8586, 1.9572] — and is the
     first measurement precise enough to support setting one. That is a
     decision for a follow-up ticket, not for this evidence file.

  5. IT DID NOT TEST SUPERVISOR RESTART BEHAVIOUR AT 5N. restartLines was 0.
     Nothing crashed, so nothing was recovered from. The claim "one supervisor
     holds 15 watchers" is established for the steady state only; the claim
     "one supervisor correctly re-attributes a restarted watcher to its own repo
     at N=3" was never exercised.

  6. IT DID NOT RUN LONG. 150 minutes against #109's 16 hours. Any slow-onset
     effect — the +1.2334 MiB/min #105 saw and #109 could not reproduce, FTS
     fragmentation, WAL pathology — is out of reach at this duration. This is a
     scale run, not a soak, and it should not be cited as one.

  7. IT DID NOT USE REAL AGENT TRAFFIC. The corpus is synthetic, generated by
     `seed116.ts` and `traffic116.ts` with per-repo marker tokens. That is what
     makes the leak query exact, and it is also why the isolation result is
     about the filtering path rather than about any property of real transcripts.
