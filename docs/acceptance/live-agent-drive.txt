CAUSE, and it is two things meeting:

  a. `scripts/acceptance/live-agents.ts:433` calls
     `retro.observeSession({...})` WITHOUT `await`, inside a loop over the
     session-metas. Two calls are therefore in flight at once.
  b. `RetroEye.persist` (`src/eyes/retro/retro.ts:966-978`) writes through a
     FIXED temp path, `${this.statePath}.tmp`. Two concurrent persists write
     the same temp file; the first `rename` moves it away and the second gets
     ENOENT.

The comment on `persist` says "Atomic (temp + rename): a crash can never tear
the cursor or the ledger". Atomic against a crash, yes. Not safe against a
second concurrent writer. The repo already has the fix pattern in tree —
`src/deploy/trust.ts` names its temp file
`${configPath}.argus.${process.pid}.${randomUUID()}.tmp` for exactly this
reason — so this is an inconsistency, not an unknown.

WHY #36 DID NOT SEE IT. The same script, the same two session-metas, the same
race: #36's run won it. A floating promise means the loser surfaces as an
unhandled rejection rather than as a failed check, so the drive's own
"16/16 checks passed" banner is blind to it — as is this file's previous
version, which recorded 16/16 and a `time` line and never recorded an exit
code. **The exit code is now in the identity block above for that reason.**

The 16/16 body below is run 2's, and every check in it is a genuine pass over
