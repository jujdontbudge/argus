4. ARGUS_LIVE_CLAUDE_SUBSCRIPTION — not-run, and WHY (a result, not a failure)
------------------------------------------------------------------------------
The Claude half of `src/deploy/live.test.ts` cannot be driven under the house
rules any more. #96 is what changed that, and nothing recorded it until now.

  1. That half spends a real subscription call, so it needs the real HOME
     (SPEC §1 item 7: no API access; capability comes from the CLI).
  2. Since #96 that half also reaches `trustDirectory`, which writes
     `$CLAUDE_CONFIG_DIR ?? $HOME` + `/.claude.json` — with the real HOME,
     Johan's own config.
  3. That file is 340 KB with 1276 project entries and was last written 23
     seconds before this was measured: his live sessions rewrite it
     continuously. `trustDirectory` read-modify-RENAMES it, so a concurrent
     write in that window is silently lost.
  4. #96's own evidence (`silent-deploy.txt`) already rules this out in as
     many words: "writing Johan's real ~/.claude.json is forbidden by the
     house rules." #96 drove its own probe under a scratch CLAUDE_CONFIG_DIR
     throughout for exactly this reason.

  MEASURED, so the tradeoff is not a guess. The obvious escape — keep the real
  HOME for credentials, point CLAUDE_CONFIG_DIR at scratch so only the trust
  write is redirected — does not work, because the binary reads credentials
  from the config dir too:

    $ cd <scratch>; CLAUDE_CONFIG_DIR=<scratch>/cfg \
        ~/.local/bin/claude -p 'say ok' --model claude-opus-5
      Not logged in · Please run /login

    ~/.claude/.credentials.json was checksummed before and after and was
    unchanged (fed88619...e7d6). It was never read, copied or written.

  So the two requirements are in direct conflict: the credential needs the
  real config dir, and the house rules forbid writing the real config dir.
  Section 3 covers what this half would have covered about the PRE-TRUST STEP
  at zero cost; it does not cover the transcript leg, and this file does not
  claim otherwise.

  TO CLOSE IT would take one of: a `trustDirectory` that can be told to skip
  (a deployment into an already-trusted ancestor never writes), an opt-in
  "assume trusted" request field, or Johan running it by hand and accepting
  the write. That is a ticket, not a thing to decide inside an evidence
  refresh.
